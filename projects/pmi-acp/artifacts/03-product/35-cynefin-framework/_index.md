# Cynefin Framework

## 📝 CUE & NOTES

| CUE | EN | VI |
|---|---|---|
| **What is it?** | A **decision-making framework** (developed by Dave Snowden) that helps leaders categorize the nature of a problem and choose the most appropriate response approach. | **Framework ra quyết định** (do Dave Snowden phát triển) giúp lãnh đạo phân loại bản chất của vấn đề và chọn cách tiếp cận phù hợp nhất. |
| **What is it used for?** | Categorizes problems into domains so teams know whether to follow best practices, good practices, experiment, or act immediately — avoiding one-size-fits-all solutions. | Phân loại vấn đề thành các miền để nhóm biết nên theo best practices, good practices, thử nghiệm hay hành động ngay — tránh giải pháp đồng nhất cho mọi tình huống. |
| **Domain 1: Simple/Clear** | **Known knowns.** Cause-and-effect is obvious. → **Sense → Categorize → Respond** using **best practices**. Example: coding software crashes → uninstall and reinstall. There IS a textbook answer. | **Đã biết rõ.** Nguyên nhân-kết quả rõ ràng. → **Nhận biết → Phân loại → Phản hồi** bằng **best practices**. Ví dụ: phần mềm lập trình bị crash → gỡ cài đặt và cài lại. CÓ câu trả lời trong sách giáo khoa. |
| **Domain 2: Complicated** | **Known unknowns.** Cause-and-effect requires analysis. → **Sense → Analyze → Respond** using **good practices**. Example: server slowing down when specific code runs — no single fix, but good practices exist (upgrade RAM, CPU). Needs expert analysis. | **Biết rằng chưa biết.** Nguyên nhân-kết quả cần phân tích. → **Nhận biết → Phân tích → Phản hồi** bằng **good practices**. Ví dụ: server chậm khi chạy code cụ thể — không có cách sửa duy nhất, nhưng có good practices (nâng cấp RAM, CPU). Cần phân tích chuyên gia. |
| **Domain 3: Complex** | **Unknown unknowns.** Cause-and-effect only understood in hindsight. → **Probe → Sense → Respond** using **emergent practices**. Example: entire system (code + server + app) failing — no documented fix; experiment to find what works. | **Chưa biết rằng chưa biết.** Nguyên nhân-kết quả chỉ hiểu được sau khi xảy ra. → **Thăm dò → Nhận biết → Phản hồi** bằng **emergent practices**. Ví dụ: toàn bộ hệ thống (code + server + app) thất bại — không có cách sửa đã ghi chép; thử nghiệm để tìm ra cái gì hiệu quả. |
| **Domain 4: Chaotic** | **No knowns.** No cause-and-effect visible. Everything is broken. → **Act → Sense → Respond** using **novel practices**. Goal: stop the bleeding FIRST, then assess. Example: all systems down, cloud disconnected — act immediately, try anything to stabilize. | **Không có gì đã biết.** Không thấy nguyên nhân-kết quả. Mọi thứ đều hỏng. → **Hành động → Nhận biết → Phản hồi** bằng **novel practices**. Mục tiêu: dừng chảy máu TRƯỚC, rồi đánh giá. Ví dụ: tất cả hệ thống sập, cloud ngắt kết nối — hành động ngay, thử bất cứ thứ gì để ổn định. |
| **Disorder (center)** | When you **cannot determine** which domain a problem belongs to. The danger zone — wrong domain = wrong approach. Must investigate further to correctly classify the problem. | Khi bạn **không thể xác định** vấn đề thuộc miền nào. Vùng nguy hiểm — sai miền = sai cách tiếp cận. Phải điều tra thêm để phân loại đúng vấn đề. |
| **Mental Model** | Think of medical triage: **Simple** = splinter (follow standard removal procedure). **Complicated** = broken bone (needs X-ray + specialist). **Complex** = unknown illness with multiple symptoms (experiment with tests). **Chaotic** = cardiac arrest (act NOW — chest compressions first, ask questions later). **Disorder** = not sure if it's serious or not. | Hãy nghĩ như phân loại y tế: **Simple** = gai đâm (theo quy trình lấy gai chuẩn). **Complicated** = gãy xương (cần X-quang + chuyên gia). **Complex** = bệnh chưa biết với nhiều triệu chứng (thử nghiệm các xét nghiệm). **Chaotic** = ngừng tim (hành động NGAY — ép tim trước, hỏi sau). **Disorder** = không chắc có nghiêm trọng không. |
| **Connections** | Links to: **CAS** (complex domain matches CAS thinking — experiment, emerge), **Risk Management** (chaotic = crisis response), **Iterative Development** (complex domain = probe-sense-respond = iterate), **Servant Leadership** (don't dictate in complex/chaotic — facilitate). | Liên kết với: **CAS** (miền complex khớp với tư duy CAS — thử nghiệm, emerge), **Risk Management** (chaotic = phản hồi khủng hoảng), **Iterative Development** (miền complex = probe-sense-respond = lặp lại), **Servant Leadership** (không độc đoán trong complex/chaotic — tạo điều kiện). |
| **Real-world Example** | Sprint issue: **Simple** — dev's IDE won't open → reinstall (best practice). **Complicated** — API response slow → analyze traffic, optimize queries (good practice). **Complex** — app works in dev but fails in prod with no clear pattern → experiment with env configs (emergent). **Chaotic** — production goes completely down during demo → roll back immediately, debug later (novel/act first). | Vấn đề sprint: **Simple** — IDE của dev không mở → cài lại (best practice). **Complicated** — phản hồi API chậm → phân tích traffic, tối ưu query (good practice). **Complex** — app chạy trong dev nhưng lỗi trong prod không rõ mô hình → thử nghiệm cấu hình môi trường (emergent). **Chaotic** — production sập hoàn toàn trong demo → rollback ngay, debug sau (novel/hành động trước). |
| **Pitfalls** | • Treating all problems as **Simple** — applying best practices to complex problems leads to failure. • Jumping straight to **Chaotic** response for complicated problems — acting without analysis wastes resources. • Staying in **Disorder** too long — failing to classify a problem delays the right response. • Confusing **Complicated** (expert analysis needed) with **Complex** (no known answer, must experiment). | • Xem tất cả vấn đề là **Simple** — áp dụng best practices cho vấn đề phức tạp dẫn đến thất bại. • Nhảy thẳng vào phản hồi **Chaotic** cho vấn đề complicated — hành động không phân tích lãng phí nguồn lực. • Ở lại **Disorder** quá lâu — không phân loại vấn đề trì hoãn phản hồi đúng. • Nhầm **Complicated** (cần phân tích chuyên gia) với **Complex** (không có câu trả lời đã biết, phải thử nghiệm). |
| **Exam Tips** | • No memorization needed — **understand the purpose**: categorize problems to choose the right response. • 4 domains + disorder center. **Simple** = best practices. **Complicated** = good practices. **Complex** = emergent/experiment. **Chaotic** = act first/novel. • If exam describes "unknown problem with no documented solution" → **Complex** domain. • "Everything is broken, act immediately" → **Chaotic** domain. • Disorder = can't determine which domain → investigate first. | • Không cần thuộc lòng — **hiểu mục đích**: phân loại vấn đề để chọn phản hồi đúng. • 4 miền + trung tâm disorder. **Simple** = best practices. **Complicated** = good practices. **Complex** = emergent/thử nghiệm. **Chaotic** = hành động trước/novel. • Nếu đề mô tả "vấn đề chưa biết không có giải pháp đã ghi chép" → miền **Complex**. • "Mọi thứ hỏng, hành động ngay" → miền **Chaotic**. • Disorder = không xác định được miền → điều tra trước. |

## 📌 SUMMARY

| EN | VI |
|---|---|
| The **Cynefin Framework** (Dave Snowden) helps leaders categorize problems into four domains — **Simple** (best practices), **Complicated** (good practices + expert analysis), **Complex** (probe and experiment), and **Chaotic** (act immediately) — plus a **Disorder** center when the domain is unclear. In agile, it helps teams choose the right problem-solving approach: follow known practices for simple/complicated issues, but experiment and adapt for complex ones, and act fast to stabilize chaos. | **Cynefin Framework** (Dave Snowden) giúp lãnh đạo phân loại vấn đề thành bốn miền — **Simple** (best practices), **Complicated** (good practices + phân tích chuyên gia), **Complex** (thăm dò và thử nghiệm) và **Chaotic** (hành động ngay) — cộng với trung tâm **Disorder** khi không rõ miền. Trong agile, nó giúp nhóm chọn cách giải quyết vấn đề đúng: theo practices đã biết cho vấn đề simple/complicated, nhưng thử nghiệm và thích nghi cho vấn đề complex, và hành động nhanh để ổn định chaos. |
